# Backtesting and Evaluation

Backtesting evaluates a forecasting approach across historical forecast origins using the same target, grain, horizon, and feature availability rules used for production scoring.

## Rolling-Origin Contracts

Backtest runs are defined by `vertex/config/backtest_contract.yaml`. A contract declares:

- the forecast contract to evaluate
- the model config to train and score
- the historical forecast origins
- the required horizons
- the training lookback window
- segment columns for metric breakdowns
- baseline models
- metric policy and promotion gates

The contract is validated before a runner trains or scores anything. Horizons must be a subset of the forecast contract horizons, origins must be explicit or generated by an origin policy, and baseline names must come from the supported baseline list.

The model configuration must declare `inputs.prediction_horizons`, and those horizons must exactly match the backtest contract. The default contract uses `favorita_store_h7_xgboost`, a direct horizon-7 model trained on `sales_store_n7d` (demand exactly seven calendar days after the forecast origin). Cumulative demand over days 1–7 is stored separately as `sales_store_n7d_cum` and is not used as the point-horizon label.

Validate a contract and inspect its expanded origin plan with:

```bash
make vertex-backtest-plan
```

## Origins and Cutoffs

Each origin represents the information set available at that point in time. For a daily next-period demand target, training data must stop before the origin if the label depends on future demand. Scoring rows use features available at the origin and produce horizon-specific forecasts.

## Baselines

The first supported baseline names are:

- `zero_demand`
- `last_observation`
- `seasonal_naive_7d`
- `same_period_last_year`
- `moving_average`
- `croston_sba_tsb`

Scoring is implemented for every listed baseline. `croston_sba_tsb` averages bias-adjusted
Croston and TSB forecasts; the individual `croston_sba` and `tsb` names are also accepted.
Scoring uses actuals available through each origin and evaluates against the actual at
`origin + horizon`. Baselines that lack sufficient history emit a null prediction so
prediction completeness remains auditable.

Run the configured direct-horizon ML model and all baselines from the model's bounded
BigQuery feature input:

```bash
make vertex-backtest
```

For each origin, model labels are limited to target dates at or before the origin; the direct
horizon model is refit and predicts the feature row at the origin. The runner bounds the query
to the necessary training, prior-year baseline, and evaluation window. When `max_entities` is
set, a deterministic entity-selection CTE applies that limit before history is downloaded.
For local testing, retain the CSV path; the CSV must contain the model's configured features
and target column:

```bash
make vertex-backtest VERTEX_BACKTEST_INPUT_MODE=csv VERTEX_BACKTEST_INPUT=path/to/history.csv
```

Pass `--baselines-only` directly to the Python CLI to retain the narrow deterministic-only
execution path.

The command prints a stable backtest run ID and aggregate/segment metric records. Append-only BigQuery table contracts are defined in `vertex/ddl/vertex_bq_tables.sql` as `backtest_runs`, `backtest_predictions`, and `backtest_metrics`. Apply them with `make vertex-bq-ddl`.

Persist a completed run and then build/test the comparison marts with:

```bash
make vertex-backtest-persist
make dbt-backtest
```

`VERTEX_BACKTEST_PERSIST=true make vertex-backtest` is equivalent to the first command.
Persistence uses insert-only `MERGE` statements keyed by `backtest_run_id`, `prediction_id`,
and `metric_id`. The same contract and input fingerprint therefore produce a no-op retry:
existing immutable rows are neither duplicated nor updated. `make dbt-backtest` applies the
Vertex DDL, builds the backtest staging, leaderboard, and champion models, and executes their
dbt tests.

The dbt staging layer exposes these records through `stg_backtest_runs`,
`stg_backtest_predictions`, and `stg_backtest_metrics`. The model leaderboard and champion
mart partition candidates by target, grain, horizon, segment, and the complete metric policy.
Rolling-origin results therefore cannot compete with legacy holdout results, and company-day
models cannot displace store-day models. Backtest runs written before these semantic columns
were introduced remain immutable and are excluded from the comparison marts; rerun those
contracts to produce eligible leaderboard records.

## Metric Policy

Backtest selection should use comparable keys:

```text
target x grain x horizon x segment_key_json x metric_policy
```

R2 is not a primary model-selection metric for demand forecasting because demand series are often intermittent, sparse, and scale-dependent. Prefer WAPE, MAE, scaled errors, bias, completeness, and quantile calibration metrics.

The scoring slice calculates WAPE, MAE, MASE, RMSSE, mean signed error (`bias`), and prediction completeness. MASE and RMSSE use each entity's pre-origin one-step naive error scale over the configured training window. If a series has too little history or a flat historical scale, its scaled-error contribution is null rather than forced to zero. WAPE is null when the sum of absolute actual demand is zero; completeness still reports normally.
